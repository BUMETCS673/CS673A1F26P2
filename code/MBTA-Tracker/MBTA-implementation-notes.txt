Boston subway map and B-branch planner

The homepage shows the full subway network, including Mattapan and Silver Line services, as schematic context. Journey planning is limited to the Green B branch: Boston College to Government Center in both directions. It preserves the team's Next.js/React stack and existing API test pages.

Data rules and limits

- The full network uses MBTA rail canonical patterns and typical Silver Line patterns. Parent-station IDs establish shared nodes; nearby bus stops are not falsely merged by name. The live B planner still uses its 23-stop canonical route. Other lines have no journey or prediction controls. Station additions remain selectable in the planner even if their drawing coordinates need updating.
- Initial load fetches a full B-line snapshot. Only explicit Refresh can request more data; swaps, station selection, focus changes and elapsed time use saved data. Predictions and vehicle observations have a 30-second cooldown, alerts 60 seconds and topology one hour. Repeated requests share in-flight work and preserve original fetch times. Existing standalone wrappers keep their original cache defaults.
- A boardable origin prediction needs a future departure; a null departure denotes a trip's last stop. Canceled (both spellings), skipped, non-revenue, and NO_DATA origin predictions are excluded.
- Destination arrival requires the same trip ID, correct route/direction/platform, a later stop sequence, and a valid arrival after departure. Vehicle IDs are not sufficient because vehicles can serve multiple future trips.
- Missing destination predictions are explicitly unavailable; skipped/canceled destination stops are labeled not served. These trains are not advertised as confirmed through journeys. No schedule fallback or invented travel-time estimate is used.
- MBTA light-rail uncertainty differs from bus uncertainty; the code does not incorrectly discard a light-rail prediction just because its uncertainty is 360 seconds.
- Displayed clock times use America/New_York. Departure countdowns use the browser clock. Predictions are estimates, not guarantees.
- Prediction and alert failures are independent. A failed alert request never becomes an “all clear.”
- Native select controls and keyboard-accessible B station targets support both directions. The map pans and zooms on narrow screens; its shortcut jumps to the planner. Camera animations respect reduced motion.

Official contracts: MBTA V3 documentation (https://api-v3.mbta.com/docs/swagger/index.html), Green-B canonical patterns (https://api-v3.mbta.com/route_patterns?filter%5Broute%5D=Green-B&include=representative_trip.stops,representative_trip.stops.parent_station), B-branch service information (https://www.mbta.com/schedules/Green-B/line).

Manual-refresh rate-limit correction

- A fixed four-entry process-local server cache shares topology, all B predictions, all B alerts and all B vehicles across selections/users. No selected-stop cache keys accumulate. A shared 429 pause honors Retry-After seconds or HTTP dates, defaults to at least 60 seconds, and prevents request storms. Other failures use 30-second exponential backoff capped at five minutes. Expired snapshots are not silently served after a failed fetch.
- Countdown ticks use absolute departure timestamps and the current wall clock; they do not fetch new telemetry or change destination ETAs. Departed trains disappear and data older than 90 seconds is explicitly out of date. Original successful fetch timestamps remain visible. Successful empty data, stale data and failed fetches remain distinct.
- Within cooldown, Refresh says Already up to date. After backoff expires, the user must explicitly Refresh; there is no automatic retry or background/focus polling.
- Synthetic handler counts: initial journey plus three swaps decreased from 9 upstream calls (1 topology,4 predictions,4 alerts) to 4 (1 topology, 1 predictions, 1 alerts, 1 vehicles). Twenty concurrent refreshes share those four initial calls. An explicit refresh at30 seconds adds predictions+vehicles; at60 seconds adds predictions+alerts+vehicles. Swaps and local ticks add zero.
- Regression tests: node --test tests/shared-mbta-cache.test.mjs tests/b-snapshot-client.test.mjs. Browser fixture test: node tests/manual-refresh.browser.cjs with a separately started isolated CDP browser on9333. MBTA_QA_URL optionally overrides default3187; MBTA_QA_OUTPUT selects output. Fixtures/fake clocks stay in QA, never production data. Updated map-label browser harness consumes the same snapshot endpoint.
- This cache is process-local; a multi-instance deployment would need shared coordination for a global upstream quota. No dependency, README, commit or push changes.

Vehicle observation correction

At 2026-10-13 22:03 UTC, the official vehicle feed reported an inbound train STOPPED_AT Boston College platform70106, headsign Government Center, while terminal predictions were empty. Scheduled departures existed separately. This confirms that empty timed predictions do not mean no train is operating. The homepage now shows a recent stopped vehicle at the selected origin when no timed prediction is available, its actual reported timestamp, and an explicit no-departure-time / boarding-unconfirmed notice. Observations expire after90 seconds, respect direction, origin platform and revenue status, and never create destination ETAs. A single full-B vehicle snapshot shares the existing manual-refresh and backoff behavior. Schedules are linked separately and are never represented as live predictions.
